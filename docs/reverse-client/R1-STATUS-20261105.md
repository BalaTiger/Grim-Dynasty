# R1 status, 2026-11-05

This is a consolidation of the R1 work performed in this session. It separates what is proven with frozen receipts, what is proven only as disk evidence, and what is blocked by the environment. It deliberately does not claim R1 acceptance.

## What has a frozen receipt

`v6` is the last recipe that ran to completion: `.tooling/r1-controller-active-integration-validation-v6/result.json` records `passed-controller-move-association-prefix`, 4/4 compilations, 21 scenarios, 394 assertions, `original_read`/`original_executed`/`backend_started`/`gameplay_accepted` all false, and the owner receipt records an empty and disposed Job.

Covered by v6: real MoveTo/Begin construction with the conditional controller association, the slot60 DWORD store, the slot80 count/state selection prefix, and the Prestart `+0x70` empty-stub path bound explicitly through `ControllerAIStateTableBinding`.

## What is proven as disk evidence but not executed

- All 24 `ControllerPlayerState` vtables and their `+0x70` targets, resolved from the saved `RegisterStates` assembly plus disk reads (`docs/reverse-client/r1-player-state-vtables/register-states-vtables.json`).
- `MoveTo` `+0x70` = `0x1663F0`, decoded as `SetState("Idle", zeroed head)` (`docs/reverse-client/r1-moveto-endofpath/inspection.json`).
- `Idle` entry `0x165B30` (exact pdata 107 bytes): builds an action, dispatches it through the already-modelled `HandleAction127DD0`, then arms a 2000 ms timer (`docs/reverse-client/r1-idle-entry-165b30/`).
- Action construction `0x081A40` and the adjacent `0x081AC0` Character class check (`docs/reverse-client/r1-action-construct-081a40/`).
- The engine/ObjectManager globals live in **Engine.dll** `.data`, proven arithmetically from `0x1C0A0`/`0x1C0DF` (`docs/reverse-client/r1-engine-global-contradiction-20261105.json`).

## What is wired in code but has no official receipt

`v8` (and its blocked predecessor `v7`) add the registry-tree scenario: `SetState` passes the header read `0x07896F`, runs the old state's `Exit`, copies the payload into `state.Data2A8` (asserted), publishes `Current2A0` as the Idle state (asserted), and stops at `0x123EE0` because the Idle entry body is not modelled. A scratch build reports 22 scenarios / 400 assertions, and that figure is explicitly **not** evidence.

`v7` and `v8` both failed the 5 GiB physical-memory gate before starting a worker: v7 saw 3.4 GiB, v8 saw 4.76 GiB (`docs/reverse-client/r1-v7-resource-gate-block-20261105.json`, `r1-v8-resource-gate-block-20261105.json`). The gate is never relaxed.

## Runtime sampling

The reader `tools/static_analysis/read_r1_runtime_pointers.py` is validated on itself and on a sibling shell (Toolhelp, PSAPI fallback, spec-driven cross-process read, 24 logic checks including an FNV value that matches the C# model's independent reference). The sampling spec is corrected to `module=Engine.dll`, `engine=0x421428`, `manager=0x4213A0`, with an enumeration route that avoids the unresolved Engine object pointer.

Two real sampling attempts were executed against a running client. Both were wrong for a now-understood reason: they read Game.dll RVAs where the values live in Engine.dll. No field value was ever claimed from those attempts, and the spec carries `invalidated-by-attempt-2` history followed by the correction.

## The click-to-move bridge

The gap is confirmed: no test composes the widget ground pick with the move request. Attempts to build it produced four real wiring fixes (`World.BindRegion`, `World.BindLevel` after construction, published empty `PathableActors`/`Neighbors`) but the intersection still throws inside `LevelIntersectionContracts.GetIntersection130130` once real ground is attached. There is no existing reference fixture for a real ground hit: `WorldIntersectionTests` only asserts misses. The skeleton `src/reverse_client_actions/ClickToMoveBridgeTests.cs` compiles and runs but throws, is in no recipe, and is not evidence.

## Update at round 33

Three official receipts now exist:

- `v6`: 21 scenarios / 394 assertions, `passed-controller-move-association-prefix`.
- `v9`: 22 scenarios / 400 assertions, the same status, and the first receipt that includes the MoveTo end-of-path chain (registry tree, Exit, payload copy, state publication).
- `ground-hit v2`: 1 scenario / 3 assertions, `passed-click-to-move-ground-hit` — a synthetic 2x2 flat ground returns an ordered positive distance while `Position08.Q0` stays Unknown.

Two things are now settled that were previously open:

1. The ground intersection contract produces a **distance**, not the hit position. The position lives in `CameraTargetState.Target120` and is transformed by `CameraTargetContracts.GetTarget`; the writer of `Target120` is not present in the saved evidence (all 72 stores to `[reg+0x120]` were checked; none is in the 41 camera-related files).
2. Because a static writer hunt is not available, the cheap route is to read `Target120` at runtime after a click. The sampler is already validated, so this needs only a loaded level.

Remaining work therefore needs the client running: `Target120` (ground position), `Character+0x26AF` (the move gate) and `Engine+0x50` (world). A single read-only sampling session with the corrected Engine.dll spec would settle all three.

## Final update (round 40)

### Confirmed at runtime on the original client

- The module correction is proven: `Engine.dll+0x421428` and `Engine.dll+0x4213A0` are live pointers while the same RVAs in `Game.dll` are code. This was the root cause of the two earlier failed sampling attempts.
- `Engine+0x50` is readable (World50), and the ObjectManager walks cleanly: 65,536 buckets, 53,324 map entries, 0 unreadable.
- The local player was identified by class, not by guessing: vtable `0x7ffa84567100` resolves through its slot0 stub to the Player class record `0x7ffa8483cab0`. The local player object is `0x22f02154b20`, controller `0x22f23229280`.
- `Character+0x26AF` is 0 in town, so the move gate is open; it was never the blocker.
- A real ground click produced the state chain `Idle (0x744e60) -> LongIdle (0x744bc8) -> MoveTo (0x744930) -> Idle`, with `Count2F0` at 0 and the overlay untouched, i.e. the cold branch.
- In the same click the character coordinates at `Player+0xD8` changed from `(120.641, 33.086, 17.381)` to `(115.192, 33.472, 24.887)` (about 9.3 units), and the user independently saw the movement in game.

That closes the "click to move" segment as an observation on the original client.

### Corrections made during this work

Two misreads were retracted rather than carried forward: `Controller+0x2A0` points at a **state object** (the vtable is `[state]`), and a `VirtualQuery` result was invalid. Earlier claims of "LongIdle" and of "MEM_FREE state" are superseded.

### Still not closed

- The ground target coordinate (`CameraTargetState.Target120`); its writer was not found in the saved evidence.
- Whether `0x1663F0` actually executed during that click (no breakpoint was used).
- What returns the controller to Idle (the 2000 ms timer versus completion).
- Presentation/rendering.
- Most importantly: the rebuilt code does **not** yet drive this behaviour. R1 acceptance therefore is not met; what exists is (a) three frozen receipts for the OWN model and (b) runtime observations of the original.
