# M3 damage entry review

This is static evidence, not a playable combat implementation or a native execution result.

`export-targets.json` resolves the named export `Character::ApplyDamage(float, PlayStatsDamageType const&, CombatAttributeType, mem::vector<unsigned int> const&)` to Game RVA `0x068930`. The exact `.pdata` interval is `[0x068930,0x068983)`, 83 bytes. `entry-bodies/inspection.json` records a complete 19-instruction byte-for-byte decode, with the original Game.dll SHA256 unchanged before/after: `cd7ecd7942d719f96b42aff4896f8c25d52152b4a41191f71a4a66ea48cecad2`.

The observed entry sequence is:

1. Preserve the character pointer; forward the fifth argument from the caller stack; call RVA `0x11D340` with `this + 0x530`.
2. After that call returns, read the 32-bit field at `character + 0x69C`, then call IAT slot RVA `0x609128` with the original character pointer.
3. Tail-call RVA `0x077EC0` with `this + 0x45F0`, integer argument `3`, the IAT return's low 32 bits, and the previously read `+0x69C` value.

There is no direct life subtraction, armour calculation, hit roll or death decision in these 83 bytes. The meaning of the tail-call's `3` and `+0x69C` cannot be established just from their values. The entry cannot be replaced with `HP -= damage` and described as recovered combat. Failure propagation, callback changes and exceptional effects inside both direct targets remain unresolved by this pass.

The direct pass subsequently read these two bodies in full: `[0x11D340,0x11D6F6)` (950 bytes, 231 decoded instructions) and `[0x077EC0,0x077F53)` (147 bytes, 41 instructions). Both have verified contiguous byte coverage in `direct-bodies/inspection.json`; the *overall pass* is marked Failed because a later equipment body contains inline table data that the linear disassembler interpreted as instructions. That report has not been relabelled as a successful whole pass.

The first dependency retains the float damage, rejects values not strictly greater than zero (the observed comparison also takes the unordered branch), and reads a double field at `qword[this+8]+0xF00` before and after processing. Positive damage involves an owner virtual call at `+0x870`, global `A66288 -> +37598`, a constant at `7A8054`, an optional float absorption field `this+0x2CC`, then a list of virtual filters at `this+0x2B0..2B8`. The absorption branch calls a logger before rereading/writing the field; filters can replace the remaining damage and stop it. No callback is assumed inert.

It then calls `0x068AB0(owner, remainingDamage, statsReference, 0, true)`, performs logging/global bookkeeping through `0x2C5BC0`, and checks the before/after `+0xF00` value. A positive-to-nonpositive transition conditionally resolves a source object using `this+0x16C`, calls `0x535A60`, and processes additional IDs through `0x49CFD0` and virtual callbacks. These bodies therefore locate the health-settlement and kill-notification dependencies; they do **not** close them. They cannot yet produce a trusted combat death for the existing KillCondition consumer. Floating-point, global state, callbacks, unknown filters and exceptional cleanup remain material conditions.

`0x077EC0` checks an initialization byte, optionally calls IAT `6097F8`, selects a 0x80-byte record using the caller-supplied index, tests its pointer/status, and calls `0x078E30` with a callback address `58F210`; a false result leads to logging. Its event meaning and callback semantics are unverified. The integer `3` alone is not a proved death-event ID.

No more native bodies were followed beyond the agreed direct pass. The next useful combat scope would be one ordinary single-target damage-to-death path (starting at `0x068AB0`) that can feed the already verified kill-condition module, with explicit Unsupported at unresolved behaviours. That is an engineering dependency, not an approval denial. It must not expand into unrelated Actor/CRT work. Original runtime execution, loader compatibility and full combat/AI remain unverified.

The separately decoded sword record has physical min/max 9/19 and an attack-speed modifier field. Those are input data, not an established random selection, cadence, defence, price or equipment algorithm. No guessed combat or trading rule has been added to the scene.

## Settlement dependency 068AB0: saved 235-byte range

The approved `damage-settlement` pass saved `[068AB0,068B9B)` with contiguous coverage (55 rows), original SHA256 unchanged. Its instruction JSON SHA256 is `29cb0371f9a2cfb9638d3d9d11e0426db5821f6740ecbc32e6dd72d314abc033`. The following is a conditional static contract, not complete `ApplyDamage` or an established death-event producer. Offsets are relative to the owner pointer received in RCX.

1. Preserve float damage from XMM1 and the borrowed stats pointer from R8. When R9B is zero, call owner vtable entry `+838`; a nonzero AL returns immediately. Only after that call returns AL=0, reread byte `owner+1F72`; nonzero also returns. R9B nonzero skips both gates. Therefore the virtual call can affect the later field observation; it must not be replaced by a cached predicate. The known `11D340` caller supplies R9B=0, so these are real dependencies of that path.
2. Convert the float damage to double and compare against double zero using `COMISD`/`JB`. For ordered nonnegative values, subtract that double from double field `+F00` and store **8 bytes**, without clamping the stored value to zero. Separately load float `+F0C`, widen its low lane to double, add the widened damage, narrow back to float and store **4 bytes**. This is a float accumulator with double intermediate arithmetic, not a persistent double accumulator. Negative/unordered comparisons skip these two stores under normal instruction completion; floating-point exception and rounding state remain conditions.
3. Set byte `+1698` to 1 even if those stores were skipped. Only if the fifth stack argument is nonzero and dword `stats[0]` equals numeric type 1, examine the death-related path. It applies `MAXSD(health,0)` to a temporary and narrows it to float; a result strictly greater than zero skips the path. **That temporary maximum does not clamp stored +F00.** Otherwise call unknown `CF6E0(owner+F78,4)`, multiply its float result by float `owner+27C8`, compare with the original float damage, and on the observed non-below comparison set byte `+27D8` to 1. This byte's meaning, CF6E0's contract, special floating values and full death processing are not established; the body does not clear an already-set +27D8.
4. All non-gated paths then call unknown `3FE390(owner+1790,originalDamage,statsPointer)` at `068B86`, including paths that skipped the numeric stores. The normal return is after that call. Prior health/accumulator/flag writes remain visible to it; no rollback is shown if it does not return. Its effects are required before claiming this settlement path complete.

The same pass's `[535A60,535A8F)` range is only a **47-byte runtime-function fragment**: it ends with `535A8D: 74 3E`, a conditional jump to `535ACD`, whose fallthrough is `535A8F`. It does not include the logical function's completion. The pinned saved instruction JSON is `5ef95490451c2d2f6c9f8af30d8eeeec57826c6778c5571d1e86768afc7e405e`. The next prepared plan is limited to those two byte-proved successors, each bounded by its containing `.pdata` fragment; already-saved proof bytes are excluded and duplicate fragments are read once. A separate plan for `3FE390` is metadata-only. Neither plan has been executed by this review, and neither follows additional callees automatically.
# Later bounded fragments and the implemented boundary

The saved `damage-notification-fragments` evidence extends the prior 47-byte `535A60` entry with only its two directly proven successors: `535A8F..535ACD` (62 bytes) and `535ACD..535AE1` (20 bytes). The empty-vector branch is an epilogue. The nonempty path loads each qword element, skips nulls, and calls `49CB80` with the borrowed arguments; it advances by 8 and freshly reads owner+230 at each loop comparison. This establishes local iteration/order, not callback semantics, concurrent/reentrant container validity, kill-event identity, or once-only delivery. The native event-11 consumer remains insufficient to prove the producer.

`damage-postprocess-body` records `3FE390..3FE40E` (126 bytes). It calls `403AC0` twice on subobject+1B8 using the same borrowed stats reference, then reads the first returned record's float+24 and writes the float sum to the second returned record's +24. If stats type is 1 and original damage exceeds subobject+74, it writes that float maximum. Lookup identity, insertion/comparison, failure and initialization are unresolved; do not collapse the two lookups or assume a no-op final hook.

The fixed `attribute-leaf-window` at `CF6E0..CF700` contains no return. It loads constant `7A8054`, uses signed `EDX` to read float arrays at `this+index*4` and `this+index*4+1D0`, and begins arithmetic. Missing `.pdata` did not justify assuming a trivial return or stopping all work. The explicit 32-byte probe is retained as incomplete; bytes beyond it were not read by that plan.

`src/combat_runtime/NativeDamageSettlement.cs` implements only the observed `068AB0` conditional contract. Native gate, attribute and final-statistics interfaces must be supplied explicitly; missing observations stop with the completed write prefix intact. `artifacts/m3-patrol-20261022-01/checks.log` records 129 passed own assertions / 11 groups. These test callbacks are not connected to the scene as substitutes for native behavior. Full attack generation, native damage/death production and runtime compatibility remain unverified.

## Statistics lookup 403AC0: existing-branch model

The saved `damage-statistics-lookup/direct-403ac0.instructions.json` (SHA256 `e62a64da70963ff2e2be991ab96b201108ad114747c0b358aa2663d9eb32c768`) covers `[403AC0,403B96)`, 214 bytes, including both normal returns. This refines the earlier unresolved lookup statement above; it does not establish native container initialization or a complete insertion implementation.

The entry takes the container in RCX, an output address in RDX, and a borrowed two-dword key in R8. It reads the head pointer at container+0, root at head+8, and each node's byte+19 terminal flag (any nonzero). On a nonterminal root it caches signed key[0] at `403AE6`. The traversal compares signed node+1C against that cached value, using `JL/JG`; only when equal does it freshly read key[1] and compare signed node+20. Smaller nodes follow +10; other nodes become the candidate and follow +0. No unsigned interpretation of the existing model's `uint? Type` is valid here: its raw bits must be converted with `unchecked((int)Type.Value)`.

At traversal end, head candidate means missing. Otherwise the function freshly reads key[0], candidate+1C, and, only if equal, candidate+20 then key[1]. A key less than the candidate takes the missing branch. The literal remaining branch is **key >= candidate**, not an added equality check. Equality follows under a stable correctly ordered tree assumption; this bounded model does not silently validate, sort, normalize or deduplicate the entire supplied graph.

The existing branch writes the candidate pointer to output+0 at `403B32`, sets RAX to the original output address at `403B35`, writes **one byte 0** at output+8 at `403B38`, then returns at `403B4B`. It does not clear output padding, write the tree, or call another function. Empty trees reach the missing branch without reading either key dword.

The missing branch stores the borrowed key pointer in a stack slot and calls `403BA0` at `403B59`, with the same container and an address of that slot. After normal return it passes the returned pointer as the stack argument, candidate in R8, returned-pointer+1C in R9, and the stack-slot address in RDX to `403BE0` at `403B72`. Only after both return does this body copy the slot's final pointer to output+0 and set output+8 to byte 1. That flag alone does not prove allocation/insertion success or failure guarantees. This existing-branch model stops **before `403B59`**, preserving caller output; it neither calls nor replaces either helper. Helper side effects and rollback on nonreturn require their separate evidence/model. Direct caller output stores occur after both calls, not before them.

`3FE390` uses the same container address and borrowed key pointer twice but retains two separate output slots. For stable unchanged relevant links, flags, compared keys and an existing branch without helper calls, both traversals select the same identity. Outside that condition, equal arguments alone do not prove identity. The first node's float+24 is read **after the second lookup returns**; the sum is stored into the second node's float+24. Then the borrowed first dword is reread; only value 1 reads/possibly updates float maximum+74. A failed lookup precedes amount/maximum stores. A later unsupported maximum observation preserves an already completed amount store, just as an unsupported final hook preserves earlier `068AB0` life/accumulator/dirty writes.

The new, separately compiled source `src/combat_runtime/NativeDamageStatistics.cs` supplies sparse mutable nodes/links, explicit nullable second-key view borrowing the original `NativeDamageStats`, literal bounded lookup, `3FE390` local final processing, and an identity-checked binding to the unchanged `Settlement.Final` interface. Serial/exclusive access is explicit; cycle/visit limits are own coverage stops, not native failure semantics. Finite binary32 arithmetic additionally requires the same stated normal-FP domain as Settlement. Duplicate keys follow the observed traversal without automatic rejection. No native initialization, missing-key helpers, callback, or default second key is invented.

`NativeDamageStatisticsTests.Main` is the dedicated own-fixture entry. Production SHA256 is `94b2b03a3591d7220286d4fa2d311d29166a98b818062470ef2de2a33a76f2e2`; test SHA256 is `be3895cc5d05378768d31eafef2b88d755696d04b36864b0a3f9e4b3215944a4`. An independent read-only review found no blocking C#5/interface, instruction-order or assertion issue. The tested domain covers signed comparison, sparse/lazy observations, missing-key stops, literal duplicate traversal, cycle/budget coverage limits, two actual lookups before the amount read, float widths, next-invocation live state and binding/failure prefixes. It does **not** simulate a second lookup independently failing or selecting a different node after an intervening external mutation: serial/exclusive access and no invented callback are explicit conditions.
