# 已有物品对象加入库存与双向闭环

已恢复Inventory::AddItemToInventory对**明确base Item主Object虚表配置、已存在非零对象**的加入路径，并与上阶段的保留对象扣除形成双向闭环。不是通过重新生成一个同名对象模拟放回，也没有把库存ID手工改回作为场景输入。

## 可用性变化和实际场景

原创QST2包含同一quest内的两个任务：交付后剩余<=1份行粮奖励75；重新持有>=2份奖励40。共享同一库存、事件管理器、钱包和奖励UID记录。

1. 从已有对象100的3份行粮整堆移出库存，17号事件驱动任务1完成；钱包50→125，UID[1]，对象有效保留。
2. 启动任务2后，由新InventoryAdd函数把**同一对象100**重新加入；16号事件驱动物品目标，钱包125→165，UID[1,2]，库存ID为[100]，对象引用身份及主堆叠3均保持。
3. 重复加入不重复库存ID或事件，但保留原代码在去重前的计数/性别更新。再移出、再加入一轮，两个已完成任务的回调均已注销，钱包仍165，UID仍[1,2]。

[原始UTF-8场景数据](inventory-roundtrip-scene.json)保存实测轨迹。最终统一构建874条固定断言、15个独立场景通过，仍为10个自有DLL；本轮29条加入与跨方向断言，未增加codec/math断言。[构建日志](inventory-add-build-output.txt)保留原输出；控制台对部分中文使用旧代码页，故场景另直接捕获UTF-8字节。

## 静态证据和严格顺序

本轮Rea 6.5.0离线既有缓存完成14次实际查询并关闭，证据在[rea-inventory-add](rea-inventory-add/)；原始PE虚表观察与Rea结果分开保存。

Inventory::AddItemToInventory（0x18031EA80）的已覆盖顺序为：

- 当库存owner等于客户端ID，或客户端ID为0时，引擎+0x1C计数作32位+1。这里只称它为该字段，不将其猜成“成功拾取数量”；重复调用也会递增。
- 用Inventory+0x24调用Item虚槽+0x580，写物品性别字段+0x874。
- 查找已有库存ID；重复则直接返回。所以上两项不能错误地放到去重检查之后。
- 新ID先发送16号事件（owner来自Inventory+0x20、item为输入ID），**然后**追加库存ID。
- 原bool参数为false且owner等于客户端时处理Item HookPack第0项；已初始化且回调明确为空的分支已覆盖。原参数为true时跳过该钩子，不跳过事件或追加。
- 最后检查蜕变兼容性。本域的base Item类型getter恒为0，因而不会登记或保存蜕变信息。

事件先于追加这一顺序由反汇编核对，不能按常见习惯反过来。已恢复的HasItem接收器只设置dirty/text字节，不在回调内评估任务或修改库存，因此函数返回后目标查询看到已追加的库存。未知额外订阅者继续在任何计数、性别、通知、追加之前拒绝。

## 主虚表和物理数量方法的统一依据

本轮明确读取Item主Object虚表`??_7Item@GAME@@6BObject@1@@`，地址0x18076A4C0，并以构造函数汇编核对其主指针赋值：+0x550指向返回0的折叠函数0x1800167E0；+0x580指向SetGender 0x1803258D0；+0x610/+0x618分别为SetStackSize/GetStackSize。其他继承子对象表或无Object后缀的表不当作主表使用。

新增BaseItemObjectTable是明确的实例/方法配置前提，不由DBR文件名或普通Item分类凭空推导，也不自动推广到派生类。已知这份主表即可为查询与反向扣除提供直接堆叠方法依据，不再要求重复配置另一个标签；主字段未知则数量未知，绝不回退旧样本。对应跨方向用例把旧样本设为999，实际读3、扣后主/副字段都为1；未知主字段仍Unsupported。

## 输入、预检及重要边界

输入包含已存在对象库、库存ID向量、明确owner和gender、稳定且相互一致的客户端快照、实际需要读取的引擎计数、明确base Item方法配置，以及同一库存/事件管理器的封闭HasItem接收器集合。全量预检通过后才提交。需要HookPack第0项时必须已初始化且回调为空；跳过钩子的原参数允许不依赖该行。外国owner不递增本地计数、不执行本地加入钩子，接收器仍保留客户端ID过滤；客户端ID0的独立计数规则另有测试。

重复ID绕过通知和钩子依赖，但仍需覆盖前置计数/性别路径。已有计数按原DWORD回绕。未知计数不是0，未知性别、客户端不稳定/不一致、未知接收器、缺失对象、错误对象配置和需要的非空钩子均在写入前Unsupported。缺失或0 ID不在“已有正常对象”支持域；没有把原函数在无效对象上的复杂副作用猜成无操作或生成新对象。

加入不改堆叠数量，也不创建/销毁对象。可选共享移出上下文仅用于清除自有DetachedObjects审计记录，要求同一库存、事件管理器和owner；它不是原生对象管理器字段。重复、往返和两任务完成验证了正常链条中不会多出库存引用或奖励。

## GiveItem上层边界

ScriptableAction_GiveItem::Execute（0x18046B890）正量路径遍历预缓存info项并调用角色虚槽，生成/激活/缓存生命周期尚未恢复；负量路径进入另一条扣除/仓库链。Character的共享Give入口0x180060A80只登记动作记录，不能拿来假称加入库存。Player::GiveItemToCharacter（0x1803D3FC0）在调用底层加入后还有姿态、控制器插入、容量失败、声音和可能掉落处理；Controller::GiveItemToPlayer（0x18015F4E0）又包含自动装备和网格插入。因此本阶段不声称恢复完整动作6或完整Player GiveItem。

构造函数、PickSparkleTime、物品工厂、随机掉落、Player姿态/装备/控制器/UI、派生类型教程和蜕变登记保存、真正销毁/对象管理器注销、仓库保存仍Unsupported。没有运行原构造器或调用这些副作用作为捷径。
